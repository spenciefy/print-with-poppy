# Spec feedback candidates from moving the store to 0.3

The published draft 0.3 (spec, guides, Operations v2, Mediated Sign-In v1, as of Oct 28 2026). See also [SPEC-FEEDBACK-SIGNIN.md](SPEC-FEEDBACK-SIGNIN.md) for the 0.2 items.

Items from the earlier delegated-keys draft that the published draft resolves, and so are dropped: Session Keys and their binding (gone), `dpop_jkt` without PAR (gone), algorithms (ES256 and PS384 are required), ended-Session retention (the Company's choice, §5.5), `refresh_token_expires_in` (removed), and the JWT-bearer grant's signed-in Sessions (gone).

| # | Section | Question | What this store does |
| --- | --- | --- | --- |
| 1 | 3.2 | `protected_resources` must be `https://{domain}` with no port, and the validator requires HTTPS URLs and a domain name, so a loopback test store (`http://localhost:5199`) can't be described accurately or validated live. | Publishes `https://localhost` as `resource` and in `protected_resources`. Suggest a stated rule for local development. |
| 2 | 5.2, 5.3 | Must an endpoint that needs no Session (a public catalog read) verify a Session header it receives, or may it ignore it? A bad header there could be refused or silently dropped. | Verifies every header sent to `/api/*`; a bad one gets `invalid_session`, a good one starts or continues the Session. |
| 3 | 5.2, 9.7 | A resource MAY cache a verified delegation until it expires (up to 24 h), but removing a `jwks_uri` key revokes its delegations "once caches of the key set expire" (§10). The two lifetimes differ. | Caches until the delegation expires. Suggest capping the cache at the key-set cache lifetime. |
| 4 | 5.3 | `htu` follows RFC 9449, but nothing says whether a request URL's query is excluded (RFC 9449 does) and how the Company's own URL is known behind proxies. | Compares scheme, host and normalized path against `PUBLIC_URL`; the query is ignored. |
| 5 | 4.1 | Companies MUST accept ES256 and PS384 for client assertions and delegations. May they accept others (RS256, EdDSA), and should the metadata say which? | Client assertions: ES256, PS384, RS256, EdDSA (listed in `token_endpoint_auth_signing_alg_values_supported`); delegations: ES256 and PS384 only. |
| 6 | 7 | The 401 challenge names the scopes to request. Some requests need any signed-in token (here, viewing the account). | Names `orders:read`. |
| 7 | 5.4 | An account change "MAY be refused with `invalid_session`". Is binding a Session to the first account it signs in to the intended reading, and does sign-out end that binding? | Keeps the first account for the Session's lifetime, even after sign-out; a new `sid` can use any account. |
| 8 | 5.5 | Sign-out is "once no refresh token the Company issued to that `client_id` for the account is still valid". Revoking one of several refresh tokens leaves the others' access tokens working. Is that intended? | Revocation ends that sign-in's access tokens only; other sign-ins of the same agent and account keep working. |
| 9 | Operations 3, 6 | "The Company decides which requests are for the same action." For an API, is a byte-identical request required, or the same meaning? An approval sent with a changed body must not apply, but the extension doesn't say what to return. | Compares the principal, method, path and canonical JSON body. A mismatched approval is treated as no approval and gets a new revision (a new `operation_id` when the request is different). |
| 10 | Operations 7 | After an operation is performed, the same request without an approval: a new operation (new `operation_id`), or the performed one? A User may well want the same thing twice. | Proposes a new operation; the old approval keeps returning the old order. |
| 11 | Operations 6 | May a Company refuse an approved, current revision because a store-specific precondition isn't met (here, the User approving each shirt mockup)? | Returns 409 `shirt_preview_approval_required` and performs nothing until the store's preview approval is recorded. |
| 12 | Operations 4 | The success response of an approved API request isn't described. | 201 with the order; while the checkout is being prepared, `Retry-After: 2` and the agent polls `GET /api/orders/{id}`. |
| 13 | Mediated 4 | "Only the `client_id` that started a sign-in can finish it." A large agent's attempt limits and sign-in throttles are then per client across all its Users. | Per-email and per-client limits (100 sign-ins an hour per client); the sandbox's captured-code reader is scoped to the client too. |
| 14 | 4.4 | `resource` on a refresh request: is the origin (with its port) an acceptable spelling of `https://{domain}` for a loopback store? | Accepts `https://{hostname}` and the origin; anything else is `invalid_target`. |
